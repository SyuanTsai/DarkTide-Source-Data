## 執行與計算

九個實際 trait ID 的完整 own I–IV 定義都把 `target_buff_data.num_stacks_on_proc` 設為 1／2／3／4；九個 actual wrapper 各自只 clone `targets_receive_rending_debuff`，沒有後置 own 覆寫。P2 精確接入 ID 的 wrapper 在其檔案第106行；同檔第19行帶 `_on_weapon_special_attacks` 的另一 ID 未綁定本項。普通 base 監聽 `on_hit`，用 `on_item_match` 與 `attacked_unit_is_minion` 過濾，並以 `is_item_slot_wielded` 限制觸發時必須持用本物品。通用 Attack 層還會依 damage type、profile `skip_on_hit_proc` 和重複事件旗標決定是否送出 on-hit；其 payload 含實際 attack_type、item、damage profile、結果與目標序號。

合格 parent event 透過 base helper 對被擊中目標加入 `rending_debuff`；helper 在命中結算後再次檢查 `HEALTH_ALIVE`，因此被該擊殺死的目標不會收到減益。helper 的31層 proc budget 不是目標上限；目標 Minion BuffExtension 依其同名 `rending_debuff` stacking instance 實際堆疊，上限為 template/max-cap 的16層。多個來源在同一目標 extension 內共用此同名 stack count；滿16後再受合格命中會刷新5秒期限但不再加層。每層提供 `rending_multiplier=0.025`，期限5秒、上限16層、加層刷新。Attack 先完成 damage calculation/`_handle_attack`，才在 `_handle_buffs` 送出 on-hit；server 隨後在 Buff extension 處理佇列。因此本次命中不回溯，目標的後續攻擊必須等 debuff/target-stat cache 更新後才使用此輸入。`damage_calculation` 再把目標 rending 輸入與武器/護甲等其他項合成並受自身上限約束，不能把 stack 顯示值等同整擊傷害百分比。

實際20個 Mark 的每個 top-level action block、profile/type assignment、template file SHA、trait import/append 行，已逐項記錄於 `thunderous-actual-route-coverage.json`，並併入本項 evidence。普通/重擊/直接特殊掃掠走 `ActionSweep`→`Attack.execute`，保留當前武器物品；push 使用 `PushAttack`→`Attack.execute` 並傳 item，不受 base attack_type 限制。例外與追加路徑逐項閉合：鏈斧9個黏附鋸齒 override 設 `skip_on_hit_proc=true`；2H 碾壓者特殊爆炸以 `attack_type=explosion`、原武器 item 排入 WeaponSystem 並逐目標呼叫 Attack；P3 電弧鎚 chain action 以原武器 item 及 `arc` type 呼叫 Attack，實際 profile 未設 skip。所有這些只在各自 profile、target Minion、來源 item 與全域 on-hit 條件均成立時可觸發。

對目標既有 `rending_debuff` 層數 `s`、等級每擊層數 `n∈{1,2,3,4}`，目標上限 `C=16`，每層 `r=0.025`：`added=min(n,C-s)`，`ΔR=added×r`。IV 對空目標 `ΔR=4×.025=.10`；對已有14層目標則 `ΔR=2×.025=.05`。`ΔR` 是 target_stat_buffs.rending_multiplier 的輸入變化，不是最終生命傷害倍率；DamageCalculation 將其與 attacker's rending、護甲類型、profile 倍率及其他條件合併並限制總 rending。
