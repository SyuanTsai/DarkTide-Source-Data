# Source technical contract v2

This repository owns the formal, source-side technical contract identified by schema `$id` `https://github.com/SyuanTsai/DarkTide-Source-Data/content/schema/v2/source-contract.schema.json` and `schemaVersion: "2.0.0"`. It is separate from the fixed W01 preview subset. This contract and its validator do not change or claim integration with the existing W01 compiler, Web consumer, Extension renderer, CI, or release artifacts.

## Files and stable interface

- Schema: [`content/schema/v2/source-contract.schema.json`](../../content/schema/v2/source-contract.schema.json)
- Synthetic positive fixture: [`content/fixtures/v2/representative-source.json`](../../content/fixtures/v2/representative-source.json)
- Importable validator and CLI: [`scripts/content/contract-validator.mjs`](../../scripts/content/contract-validator.mjs)
- Contract tests: [`tests/contract-v2.test.mjs`](../../tests/contract-v2.test.mjs)

The validator exports `CONTRACT_SCHEMA_ID`, `CONTRACT_VERSION`, `CONTRACT_RECORD_KINDS`, `CONTRACT_UNITS`, `loadContractSchema({ sourceRoot })`, `loadRepresentativeFixture({ sourceRoot })`, `assertSchemaValidatorParity(schema)`, `validateSourceContract(document, { schema, sourceRoot })`, `validateSourceContractFromDisk(document, { sourceRoot })`, `computeReviewDigests(document, target)`, and `createReviewReceipt(document, target, { decision, reviewer, reviewedAt })`. Import consumers can load the schema by its fixed path and pin its `$id` plus file SHA-256. The root fixture has `schemaVersion`, `contractKind`, `fixtureOnly`, `publicationEligible`, `gameReleases`, `sourceRefs`, `records`, `tombstones`, and `reviewReceipts`; its registry identity is the composite `(recordId, gameReleaseId)`.

The read-only CLI is `node scripts/content/contract-validator.mjs --check [--source-root <repository-root>]`, also exposed as `npm run content:contract:validate`. It accepts no output path and writes only a deterministic JSON validation receipt to stdout. It always reads the fixed schema and representative fixture under the selected repository root. Exit code is `0` for a valid fixture, `1` for contract errors, and `2` for invalid CLI arguments or I/O errors. The receipt contains the canonical document digest, raw schema and fixture byte digests, the derived publication state, and a `receiptSha256` over the canonical sorted JSON fields `schemaId`, `schemaVersion`, `contractSha256`, `result`, and `publicationEligible`.

The semantic checker covers every JSON Schema keyword used by this schema, then enforces cross-file identity, provenance, references, units, comparison, coverage, and review rules. Game-tested claims and game-change verification require a same-release `game-tested` evidence record backed by a `game-test` source ref; code evidence may remain alongside that evidence but cannot establish a game-tested basis by itself. This validates the declared evidence shape, not whether a human actually ran or authenticated a game test. The schema and executable kind/unit/reason registries are checked against each other. `Test-Json` may also be used as an independent local draft-2020-12 schema check; it is not a CLI or CI dependency.

## Record model and source boundary

The closed `kind` registry covers `skill`, `blessing`, `blessing-variant`, `weapon`, `attack-profile`, `stat-definition`, `stat-curve`, `damage-profile`, `armor-class`, `target-profile`, `modifier-rule`, `claim`, `evidence`, `term`, `catalog`, `curio`, `perk`, `classification`, `game-change`, and `release-compatibility`. Each kind has a strict payload schema with required identity and typed fields; arbitrary payloads and executable rule/interpreter keys are rejected.

Each record has owner `source`, a stable `recordId`, `gameReleaseId`, source links, coverage, required field-and-dimension review targets, and a derived review state. A stable ID is independent of game release. The same ID may appear in more than one release as separate composite identities, but it cannot change kind or return after a tombstone. Aliases preserve changed labels; a tombstone must follow an earlier record and cannot coexist with the ID in that release.

Game-release metadata records the three-part game version, build, monotonically ordered release ID, and immutable snapshot ID with manifest/content SHA-256 digests. A source ref binds to that release and snapshot. Public code sources require an HTTPS repository, public URL, commit, and repository-relative path. Official-document, public-data, and archive sources require a public HTTPS URL. `private-derived` evidence carries only a safe source ID, game release/build, snapshot hashes, tool name/version/hash, artifact SHA-256, and safe summary; it must not contain a private repository, URL, commit locator, or path. No private raw file or locator is part of the public contract.

References resolve by `(recordId, gameReleaseId)` and must have the required target kind. Same-release is the default. A cross-release source or record reference requires an explicit `release-compatibility` record in the referring release whose `fromGameReleaseId` is the target release and whose `toGameReleaseId` is the referring release. Version labels alone do not establish compatibility.

## Values and coverage

Finite decimal values are strings, preserving exact zero, precision, and negative values without floating-point conversion. Known scalars and ranges require declared units. A range also retains inclusive bounds and a decimal step; `step: "0"` denotes no discrete step. Panel, theoretical, and obtainable stat ranges are separate and each may be known, unknown with a bounded reason, or not applicable. Curves preserve ordered input/output knots, units, and source interpolation/edge policies. The validator checks strict input ordering and input/output unit agreement, but does not calculate damage or interpolate a curve.

Blessing variants keep `definedTiers` separate from `obtainableTiers`. The latter is either `{ "status": "known", "tiers": [...] }`, an explicit unknown value, or not applicable. A known empty tier set means none are obtainable; unknown is not treated as an empty set. Tier values must use defined tiers.

Attack contexts can preserve critical and weakspot state together with distance, charge, target order, projectile penetration, cleave, weapon marks/templates, attack/target/armor refs, talent/skill, blessing variant/tier, perk and modifier references, and explicit stat comparison points. Damage profiles retain conditional segments. Target hit zones retain armor, critical eligibility, weakspot state, and separate critical-by-weakspot multipliers. These are source facts only; no final-damage calculator is implemented. Modifier rules retain operation/grouping, stacking and descriptive trigger/exclusion/cap/duration/expiry/rounding/clamp fields as data, never executable AST.

`dataCoverage` is import completeness, not source truth. `NOT_IMPORTED` is accepted only in its `missing` entries and cannot be a typed unknown reason. It may identify a declared optional field that is absent or an empty placeholder list. `unknown` means the source value is unavailable, conflicting, unverified, or not exposed; it never means “not imported.” Complete coverage has no missing entries; partial/unknown coverage names its missing paths.

## Claims, review and game changes

Claims bind a target, property/value, applicability context, evidence, and basis. Evidence resolves to a source ref and a safe summary. Each record lists required review target pairs of JSON Pointer field path and dimension (`technical`, `evidence`, `context`, `identity`, or `compatibility`). A receipt binds one pair to a target digest, dependency digest, decision, human reviewer ID, and timestamp. A hand-set `reviewState: "approved"` without matching receipts is rejected. Any changed target or dependency makes the derived state stale; changes outside that dependency closure leave it current. The dependency digest includes traversed record payloads and applicability links, each linked release's version/build/manifest/content snapshot hashes, source artifact/tool/content digests, and explicit cross-release compatibility records. Trace-only commit fields are retained in provenance but excluded from review digests when applicable content hashes and release applicability are unchanged. A root entity's forward `claimRefs` are followed to full claim dependencies, so changing a referenced claim value stales the entity review. That claim closure continues across forward full entity/applicability references, including nested skill, perk, term, curio, and stat dependencies. When a claim points back to its target or another applicability entity, that linked node uses an identity/applicability projection; its reverse `claimRefs` are validated but omitted from that dependency path, so sibling claim edits do not stale an unrelated claim review. Comparison `statRef` links retain the referenced stat payload as a full dependency but do not pull in sibling claims. A later forward full reference can upgrade the same node from identity to full dependency and continue its claim closure. Target identity, claim context, evidence, compatibility, source content, release version/build, and snapshot content remain dependencies. Traversal is bounded by a visited set. Cycle detection separately omits intentional relationship edges (`claimRefs`, `targetRef`, `blessingRef`, and variant `weaponRefs`).

For each full node whose forward claim closure is followed, its `claimRefs` list is included in the dependency digest. Changing which claim is linked therefore stales review even when both claims remain reachable through other paths.

The contract validates that receipts are structurally attributed to a human and are current; it does not authenticate a human identity or replace the separately recorded approval event. A fixture never contains a human-approved receipt. Formal approval must come from the real review process, not a CI result or a state flag.

A `game-change` record compares an earlier release with its later target release by exact game version, build, and snapshot ID; the releases must have different manifest or content digests. It names changed entity fields, values, units, verification method, evidence, and optional superseded change. A `modified` field must have distinct before/after values using exact decimal comparison. It is attached to the target release. The schema has no MOD-impact or consumer-assessment field, and a Source database correction is not represented as a game change.

## Fixtures and validation limits

The checked-in representative fixture uses synthetic game IDs, versions, builds, hashes, and `example.invalid` source URLs. It includes all 20 record kinds, a private-derived provenance example with no locator, a public-code provenance example, two releases, a stable ID across releases, explicit compatibility, a tombstone, all relevant numeric/profile shapes, known zero, unknown range/tier values, `NOT_IMPORTED` coverage, and pending review targets. It always declares `fixtureOnly: true` and `publicationEligible: false`; it is not evidence about any real game build and cannot authorize publication.

Negative cases are built by mutating a structured clone of that positive fixture in the tests: missing provenance, untyped payload keys, dangling/wrong-kind/cross-release refs, duplicate/reused IDs, wrong units, `NOT_IMPORTED` used as unknown, stale receipts, malformed input, mismatched game comparisons, and MOD-impact fields. All validation is read-only and has no automatic import or approval side effects.
